# ElephantRoute 登录入口与启动链路修复设计

日期：2026-08-29

## 目标

- 未认证用户首次打开应用时直接看到登录表单，不经过黑色加载页或“服务不可用”中间页。
- 登录、加载和连接异常入口固定使用浅色 Aurora 卡片视觉；认证后的 FlClash 主界面继续跟随系统主题。
- 修复登录按钮持续加载但没有进入主界面的死锁，并让认证错误与订阅同步错误可区分、可恢复。

## 已确认根因

当前登录链路为：API 登录 → 用户信息 → 订阅地址 → 下载受管订阅 → `coreController.validateConfig` → 设置认证成功 → 启动核心。

`validateConfig` 依赖已经运行的 `FlClashCore`，但核心只有在登录 Future 返回后才启动，因此有效账号会卡在订阅校验阶段。运行时证据为：按钮进入持续加载，主进程没有 TCP 连接，同时没有 `FlClashCore` 进程。

## 方案

采用“认证与订阅初始化分阶段”方案：

1. API 登录成功后只获取用户信息、保存安全 token，并立即建立认证会话。
2. `GlobalState.startAuthenticatedRuntime` 启动核心并初始化核心状态。
3. 核心可用后获取订阅地址、下载并校验“大象网络受管订阅”。
4. 订阅同步失败时保留已认证会话，在界面中提示可重试错误；不得把用户退出或切换到全屏“服务不可用”。
5. 退出登录仍停止连接并删除受管订阅，用户自行添加的配置保持不变。

不采用以下方案：

- 仅把“服务不可用”换成登录页：不能消除核心启动顺序死锁。
- 登录前先启动核心：破坏“强制登录后才启动代理运行时”的边界。
- 绕过核心配置校验：可能把无效 Clash 配置写入正式数据库。

## 入口界面

- `loading`、`unauthenticated`、`authenticating` 和 `unavailable` 都在同一浅色登录壳内呈现，不再切换黑色 Scaffold。
- 视觉采用已确认的 A 方案：灰白背景、极浅绿蓝光晕、白色卡片、绿色主按钮。
- `loading` 只表现为表单上方的轻量状态，不阻止首次看到登录界面；`authenticating` 禁用输入并在主按钮中显示进度。
- 登录失败在表单内显示明确错误；网络/服务失败允许原地重试，不进入独立错误页。
- 仅入口页强制浅色主题，认证后的主界面不受影响。

## 错误与日志

- 401/403 或服务端明确拒绝显示账号或密码错误；网络异常显示连接失败；订阅同步异常显示订阅加载失败并允许后续重试。
- 日志仅记录阶段、状态码、异常类型和耗时，不记录邮箱、密码、token、快速登录 URL 或订阅 URL。
- 关键异步阶段必须有超时或可返回的错误路径，禁止再次出现无限加载。

## 验证

- 单元测试证明登录在核心尚未启动时可以完成认证，且不会提前调用受管订阅校验。
- 单元测试证明核心启动后才执行订阅同步；同步失败仍保持认证状态。
- Widget 测试覆盖首次加载、登录中、认证失败和不可用状态均使用浅色登录页。
- 运行 Flutter 格式化、聚焦测试、完整测试、静态分析和 macOS Release 构建。
- 在本机安装新构建后，以测试操作确认按钮会发起登录、核心按顺序启动且界面不再无限加载。
